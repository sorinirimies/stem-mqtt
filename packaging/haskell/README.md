# Haskell bindings

Generated by [`uniffi-bindgen-haskell`](https://github.com/mercury/uniffi-bindgen-haskell),
which at the pinned revision has three bugs that make bindings for this API unusable:

1. constructors with buffer-typed arguments never lower them (generated code doesn't compile),
2. `#[uniffi(flat_error)]` enums lose their message (decoder fails with "left N trailing bytes"),
3. records sharing a field name need `DuplicateRecordFields` in the public module.

[`uniffi-bindgen-haskell.patch`](uniffi-bindgen-haskell.patch) fixes all three; `scripts/install_bindgens.nu`
builds the generator from the pinned revision with it applied (`scripts/bindings/source.nu`).
The same fix, with new e2e fixtures, is proposed upstream:
**https://github.com/mercury/uniffi-bindgen-haskell/pull/3**. When it merges, bump the `--rev` in
`scripts/bindings/spec.nu`, delete the patch and the `patch`/`crate_path` fields, and this directory
shrinks to `cabal-header.txt`.

## Why not avoid the patch from our side?

Only bug 1 can be sidestepped without changing the public API (expose `new_mqtt_client(options)` as a
free function instead of a constructor). Bugs 2 and 3 can't: avoiding them would mean renaming public
record fields (`port`, `reason_code`, `topic`, ...) and turning every error into a non-flat enum, a
breaking change for every other language. A one-time generator fix is far less logic than carrying
that into the Rust API.

## Callbacks

Callback interfaces are exposed only as opaque handles, so a Haskell program cannot implement
`MqttMessageListener` & co. Use the pull-style API: `mqttClientEnableMessageQueue` /
`mqttClientNextMessage` and `mqttBrokerEnableEventQueue` / `mqttBrokerNextEvent`.
